## 1. PHÂN TÍCH CỔ CHAI LFM2.5-1.2B-Instruct

### Kiến trúc LFM2.5 vs Transformer

LFM2.5 là mô hình **lai Recurrent + Attention** (Liquid Foundation Model):

- **Recurrent layers** (chiếm đa số): Nén context thành trạng thái cố định → O(1) memory per decode step, KHÔNG đọc KV cache.
- **Attention layers** (thiểu số, GQA): Vẫn dùng KV cache nhưng rất ít layers → bandwidth thấp hơn nhiều so với Transformer thuần.

### Breakdown TPOT = 4ms (FP8 Weights, Batch ≈ 32 sequences)

| Thành phần                          | Thời gian ước tính | Tỉ lệ |
| :---------------------------------- | :----------------: | :---: |
| **Weight reads (FP8, 1.2GB)**       |      ~1.75 ms      |  44%  |
| **KV cache reads (attention)**      |      ~0.60 ms      |  15%  |
| **Recurrent state update**          |      ~0.40 ms      |  10%  |
| **Computation (MatMul + Act)**      |      ~0.50 ms      |  13%  |
| **Overhead (kernel launch, sched)** |      ~0.75 ms      |  18%  |
| **Tổng**                            |    **~4.00 ms**    | 100%  |

> [!IMPORTANT]
> **Phát hiện then chốt**: Weight reads chiếm **44%** thời gian TPOT. Đây là đòn bẩy lớn nhất. Giảm kích thước weights từ FP8 (1 byte) xuống INT4 (0.5 byte) sẽ giảm ~0.87ms, kéo TPOT xuống ~3.1ms. Kết hợp CUDA Graphs giảm overhead kernel launch, tiềm năng đạt ~2.5ms.

### Track A: Custom Docker Image + Custom Kernels & Online FP8 ⭐ (ƯU TIÊN #1)

**Mục tiêu**: Giảm TPOT từ 4ms → ~2.8ms, TTFT từ 73ms → ~55ms.
**Kỳ vọng điểm**: 60-70 điểm.

> [!IMPORTANT]
> **Tuân thủ quy chế chống gian lận (Mục 5):** Thí sinh không được tự ý can thiệp tokenizer hoặc thay đổi weights offline (không dùng AWQ/GPTQ offline weights). Thư mục `/model` chứa weights gốc là cố định.
> Do đó, Track A tập trung vào việc dùng Custom Docker Image để **tiêm (inject) custom Triton/CUDA kernels** tăng tốc tính toán trực tiếp trên weights gốc và KV Cache được lượng tử hóa online.

#### Bước 1: Viết và tối ưu hóa Custom Triton/CUDA Kernels cho LFM recurrent layers

Viết custom kernels tối ưu hóa các phép tính tuần hoàn (gated short-convolution blocks) của LFM2.5 và fusion layers (như LayerNorm + Linear + Activation) để chạy trực tiếp trên GPU.

#### Bước 2: Build Custom Docker Image (tái sử dụng hạ tầng Round 1)

```dockerfile
FROM vllm/vllm-openai:v0.22.1

# Cài đặt các custom kernels đã compiled
COPY ./custom_kernels /app/custom_kernels
RUN cd /app/custom_kernels && pip install .

# Setup hijack script để tiêm custom kernels lúc start
COPY ./hijack /app/hijack
ENV VLLM_CUSTOM_KERNEL=1
```

```bash
# Build và push image lên Docker Hub
docker build -t ptquanh/vllm-lfm25-custom-kernels:v1 .
docker push ptquanh/vllm-lfm25-custom-kernels:v1
```

#### Bước 3: Docker Compose chạy với Custom Image & Online FP8

```yaml
services:
  model:
    image: ptquanh/vllm-lfm25-custom-kernels:v1
    environment:
      - OMP_NUM_THREADS=2
    entrypoint:
      - python3
      - -m
      - vllm.entrypoints.openai.api_server
    command:
      - --model=/model # Giữ nguyên model gốc theo đúng quy định BTC
      - --served-model-name=LFM2.5-1.2B-Instruct
      - --host=0.0.0.0
      - --port=8000
      - --max-model-len=32768
      - --gpu-memory-utilization=0.95
      - --tensor-parallel-size=1
      - --enable-prefix-caching
      - --quantization=fp8 # Sử dụng online quantization hợp lệ của vLLM
      - --no-enable-log-requests
      - --disable-log-stats
      - --max-num-seqs=32
      - --enable-chunked-prefill
      - --max-num-batched-tokens=4096
    ports:
      - "8000:8000"
    shm_size: "2g"
    deploy:
      resources:
        reservations:
          devices:
            - driver: nvidia
              count: 1
              capabilities: [gpu]
```

> [!WARNING]
> **Rủi ro chính của Track A:**
>
> 1. Thiết kế recurrent layers của LFM2.5 rất đặc thù, việc fused kernel tự viết đòi hỏi kiểm thử kỹ để không bị sai lệch accuracy (hậu kiểm GPQA).
> 2. JIT overhead của custom kernels khi khởi chạy lần đầu có thể làm tăng TTFT của request đầu tiên (cần warmup cẩn thận).

### Track B: Advanced vLLM Flags trên Stock Image ⭐ (ƯU TIÊN #2 — An toàn)

**Mục tiêu**: Vắt kiệt mọi cải tiến có thể từ stock image `vllm/vllm-openai:v0.22.1`.
**Kỳ vọng điểm**: 57-62 điểm (cải thiện tăng dần từ mốc 56.79).

Dựa trên Golden Baseline ngày 17/07 (Slot 4 = 56.79 điểm), thử nghiệm các flag chưa từng test:

#### Nhóm B1: Compilation & CUDA Graph Optimization (3 slots)

| Slot | Cấu hình thay đổi so với Slot 4         | Mục tiêu                                                                                  |
| :--: | :-------------------------------------- | :---------------------------------------------------------------------------------------- |
|  1   | + `--compilation-config '{"level": 3}'` | Bật tối ưu hóa torch.compile aggressive (operator fusion + CUDA graph nâng cao).          |
|  2   | + `--compilation-config '{"level": 2}'` | So sánh với level 3 để chọn mức tối ưu an toàn nhất.                                      |
|  3   | + `--enforce-eager`                     | Tắt hoàn toàn CUDA Graphs để đo baseline thuần eager → xác nhận CUDA Graphs có lợi không. |

#### Nhóm B2: Scheduler & Batching Tuning (4 slots)

| Slot | Cấu hình thay đổi so với Slot 4   | Mục tiêu                                                                         |
| :--: | :-------------------------------- | :------------------------------------------------------------------------------- |
|  4   | + `--max-num-batched-tokens=3072` | Chunk size 3072 (giữa 2048 và 4096) — tìm điểm sweet-spot chi tiết hơn.          |
|  5   | + `--max-num-batched-tokens=5120` | Chunk size 5120 — kiểm tra xem lớn hơn 4096 có tốt hơn không.                    |
|  6   | + `--max-num-batched-tokens=6144` | Chunk size 6144 — gần giới hạn context input (4K tokens).                        |
|  7   | + `--block-size=8`                | Giảm block size KV cache từ 16 (mặc định) xuống 8 → giảm internal fragmentation. |

#### Nhóm B3: N-gram Speculative Decoding (3 slots)

N-gram speculation KHÔNG cần draft model, chỉ dùng pattern matching trên text đã sinh → zero overhead loading, hoạt động trên stock image.

| Slot | Cấu hình thay đổi so với Slot 4                                                                | Mục tiêu                                                                      |
| :--: | :--------------------------------------------------------------------------------------------- | :---------------------------------------------------------------------------- |
|  8   | + `--speculative-model [ngram]` + `--ngram-prompt-lookup-max=4` + `--num-speculative-tokens=3` | N-gram 4-token window, sinh 3 token speculative → đánh giá tác động lên TPOT. |
|  9   | + `--speculative-model [ngram]` + `--ngram-prompt-lookup-max=6` + `--num-speculative-tokens=5` | N-gram 6-token window, sinh 5 token speculative → mức aggressive hơn.         |
|  10  | + `--speculative-model [ngram]` + `--ngram-prompt-lookup-max=3` + `--num-speculative-tokens=2` | N-gram 3-token window, sinh 2 token speculative → mức conservative.           |

> [!NOTE]
> **Tại sao N-gram có thể giúp LFM2.5?**
>
> - Workload benchmark là hội thoại 6 turns với context ~4K tokens → nhiều pattern lặp lại.
> - LFM2.5 sinh tối đa 200 tokens/request → output ngắn, acceptance rate cao.
> - N-gram không tiêu tốn VRAM/CPU bổ sung (khác speculative decoding với draft model).

#### Nhóm B4: Combo & Fine-tune (5 slots)

Kết hợp các flag tốt nhất từ B1-B3 vào Golden Baseline:

| Slot | Cấu hình                                              | Mục tiêu                                                        |
| :--: | :---------------------------------------------------- | :-------------------------------------------------------------- |
|  11  | Slot 4 + Compilation level tốt nhất + N-gram tốt nhất | Combo tối ưu nhất trên stock image.                             |
|  12  | Slot 4 + `--max-num-seqs=48`                          | Tăng concurrency lên 48 xem có tối ưu hàng đợi scheduler không. |
|  13  | Slot 4 + `--max-num-seqs=24`                          | Giảm concurrency xuống 24 xem TPOT có giảm đáng kể không.       |
|  14  | Slot 4 + `OMP_NUM_THREADS=3` + Chunk=4096             | Thử lại OMP=3 trên nền FP8+Chunk (chưa test combo này).         |
|  15  | Slot 4 + `--disable-async-output-proc`                | Tắt async output để giảm jitter latency trên CPU 3 core.        |
