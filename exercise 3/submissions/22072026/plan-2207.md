### Công thức ERS (mỗi request):

```
S_request = 0.5 × s_ttft + 0.5 × s_tpot

s_ttft = clamp((400 - TTFT) / (400 - 10), 0, 1) ^ 2
s_tpot = clamp((10 - TPOT) / (10 - 1), 0, 1) ^ 2
```

### Tính toán điểm hiện tại (Best Config: TTFT=44ms, TPOT=4ms):

```
s_ttft = ((400 - 44) / 390)^2 = (356/390)^2 = 0.9128^2 = 0.8332

## ⚠️ TẠI SAO TPOT = 4ms LÀ CỨNG? VÀ CÁCH PHÁ VỠ

### Phân tích Bottleneck vật lý:

```
LFM2.5-1.2B với FP8 online (dynamic quantization):
- Params: 1.2B × 1 byte (FP8) = 1.2 GB weights
- MiG H200 1/4: ~1.2 TB/s HBM bandwidth (18GB partition)
- Weight read time: 1.2 GB / 1.2 TB/s = 1.0 ms (lý thuyết tối thiểu)
- Overhead thực tế: +3ms (kernel launch, attention, FP8 dequant, scheduler, conv state)
- → TPOT thực tế = 4ms
```

### 6 CÁNH CỬA PHÁ VỠ TPOT = 4ms:

|  #  | Kỹ thuật                                | Cơ chế giảm TPOT                                                    | TPOT dự kiến | Khả thi? | Rủi ro                                                           |
| :-: | :-------------------------------------- | :------------------------------------------------------------------ | :----------: | :------: | :--------------------------------------------------------------- |
|  1  | **Bỏ FP8 Dynamic → BF16 thuần**         | Loại bỏ overhead dequantization FP8 runtime (~1ms)                  |   ~3-3.5ms   | ⭐⭐⭐⭐ | VRAM tăng gấp 2, cần kiểm tra fit MiG 18GB                       |
|  2  | **vLLM V1 Modern Engine** (v0.25+)      | C++ scheduler, near-zero CPU overhead, tối ưu batch pipeline        |    ~3.5ms    |  ⭐⭐⭐  | Đã build Image v11, chờ kết quả Slot 09                          |
|  3  | **Multi-Step Scheduling**               | Giảm CPU↔GPU sync overhead bằng cách batch N decode steps liền nhau |   ~3-3.5ms   |  ⭐⭐⭐  | vLLM V1 có thể tự động bật, cần kiểm tra `--num-scheduler-steps` |
|  4  | **Giảm max_num_seqs → 8-16**            | Scheduler xử lý ít request hơn → giảm overhead mỗi iteration        |    ~3.5ms    |   ⭐⭐   | Tăng Failed Count nếu burst Poisson đến cùng lúc                 |
|  5  | **CUDA Graph Capture toàn decode path** | Loại bỏ hoàn toàn kernel launch overhead cho decode                 |    ~3.5ms    |  ⭐⭐⭐  | Đã dùng FULL mode, cần kiểm tra V1 có tương thích không          |
|  6  | **Custom CUDA Kernel cho LFM Conv1D**   | Thay thế PyTorch Conv1D bằng Fused CUDA Kernel viết tay             |   ~2-2.5ms   |    ⭐    | Cực kỳ phức tạp, cần deep knowledge LFM architecture             |

> [!IMPORTANT]
> **Phát hiện cực kỳ quan trọng từ research**: FP8 **Dynamic** quantization (`--quantization fp8`) tạo overhead
> dequantization **runtime** mỗi token (~0.5-1ms). Nếu chạy BF16 thuần (bỏ `--quantization fp8`), TPOT có thể
> giảm từ 4ms → 3-3.5ms! Trade-off: VRAM tăng từ ~1.2GB → ~2.4GB weights, nhưng LFM2.5 chỉ 1.2B params
> nên BF16 (2.4GB) vẫn dư sức fit trong 18GB MiG H200.
>
> **Top teams (83đ) có thể đang chạy BF16 + vLLM V1 + tối ưu CUDA Graph = TPOT ~1.5-2ms!**

## 🔬 CHI TIẾT KỸ THUẬT: THỬ NGHIỆM BF16 (Slot 10 - THEN CHỐT)

### Tại sao BF16 có thể nhanh hơn FP8 Dynamic trên MiG H200?

1. **FP8 Dynamic Overhead**: vLLM `--quantization fp8` tính toán scaling factors **runtime** cho mỗi forward pass → thêm ~0.5-1ms/token
2. **BF16 Native**: H200 có FP/BF16 Tensor Core chạy ở tốc độ native, zero overhead dequant
3. **Memory Trade-off**: BF16 weights = 2.4GB vs FP8 = 1.2GB. Nhưng MiG H200 có 18GB → dư 15.6GB cho KV cache (đủ cho 4400 token context × 70 conversations)
4. **KV Cache**: Với BF16 weights, vẫn có thể dùng `--kv-cache-dtype auto` (FP16) hoặc thậm chí bỏ luôn FP8 KV cache

```
ERS = 83.32 → S_request ≈ 0.8332 (giả sử 0 failed, penalty=1)
