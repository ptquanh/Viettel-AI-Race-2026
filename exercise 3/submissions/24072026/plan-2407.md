## 1. PHÂN TÍCH TOÁN HỌC — TẠI SAO 70đ BẮT BUỘC CẦN TPOT=3ms

### 1.1 Công thức Scoring (Challenge Spec)

```
s_ttft = [clamp((400 - TTFT) / 390, 0, 1)]²
s_tpot = [clamp((10 - TPOT) / 9, 0, 1)]²
S_request = 0.5 × s_ttft + 0.5 × s_tpot
Score = 100 × ERS × f(Δ)    [f(Δ)=1 nếu accuracy drop ≤ 10%]
```

### 1.2 Bảng tính ngược — Mục tiêu 70 điểm

| TPOT    | s_tpot | TTFT avg cần | s_ttft cần | Score lý thuyết | Khả thi?                             |
| ------- | ------ | ------------ | ---------- | --------------- | ------------------------------------ |
| **4ms** | 0.4444 | **18.7ms**   | 0.9556     | 70.00           | ❌ **BẤT KHẢ THI** (P50 min = 44ms)  |
| **3ms** | 0.6049 | **52.3ms**   | 0.7951     | 70.00           | ✅ **KHẢ THI** (P50 hiện = 47ms)     |
| 2.5ms   | 0.6944 | 75.3ms       | 0.7056     | 70.00           | ✅ Rất dễ nhưng TPOT 2.5ms cực khó   |
| 2ms     | 0.7901 | 95.4ms       | 0.6099     | 70.00           | ✅ Rất dễ nhưng TPOT 2ms phi thực tế |

### 1.3 Kết luận SỐNG CÒN

> 🔴 **TPOT=4ms → Trần tuyệt đối ~64đ** (kể cả TTFT=0ms + 0 failures).
>
> 🟢 **TPOT=3ms + TTFT avg=47ms hiện tại → Score ≈ 71.2đ → VƯỢT MỐC 70!**
>
> **Toàn bộ chiến lược phải xoay quanh 1 câu hỏi duy nhất: LÀM SAO GIẢM TPOT TỪ 4ms XUỐNG 3ms?**

### 1.4 Tại sao TPOT kẹt ở 4ms — Phân tích Bandwidth

Phần cứng BTC: **MIG H200 18GB** (~1/8 GPU H200 SXM5, bandwidth ~0.6-0.7 TB/s)

| Thành phần                | FP8 (1 byte/param)   | INT4 (0.5 byte/param) |
| ------------------------- | -------------------- | --------------------- |
| Weight read (1.2B)        | **1.2 GB → ~1.85ms** | **0.6 GB → ~0.92ms**  |
| Activation + KV + misc    | ~0.1ms               | ~0.1ms                |
| Overhead (scheduler+sync) | ~2.0ms               | ~2.0ms                |
| **TPOT tổng**             | **~3.95ms → báo 4**  | **~3.02ms → báo 3?**  |

**Kết luận**: Chỉ có **INT4 quantization** mới đủ sức giảm weight read time xuống nửa, kéo TPOT qua ngưỡng 3ms.

## 3. BA CON ĐƯỜNG CÒN LẠI ĐẾN 70 ĐIỂM

### 🟢 Path A: Online INT4 Quantization — Image v15 MỚI (Xác suất đạt 70đ: 25%)

**Đây là con đường DUY NHẤT có cơ sở toán học đạt 70đ.**

**Ý tưởng**: Xây image mới quantize model sang W4A16 **tại runtime** (= Online Quantization, TUÂN THỦ luật BTC mục 4).

**Cơ chế kỹ thuật**:

```
Container start → Load FP8/BF16 weights từ /model
→ Chạy torchao int4_weight_only(group_size=128) trên tất cả Linear layers
→ Weights giảm 1.2GB → 0.6GB
→ Decode: Weight read 0.6GB / 0.65 TB/s ≈ 0.92ms
→ TPOT = 0.92ms + 2ms overhead ≈ 3.0ms → Grader báo 3ms!
→ Score = 0.5 × s_ttft(47ms) + 0.5 × s_tpot(3ms) = 0.5 × 0.821 + 0.5 × 0.605 = 71.3đ 🎯
```

**Tuân thủ luật BTC**:

- ✅ Mục 4: "Quantization: Các kỹ thuật Online Quantization" → INT4 qua torchao tại runtime
- ✅ Mục 5: "Không can thiệp trái phép vào weights" → weights được quantize online, checkpoint `/model` trên disk KHÔNG BỊ SỬA

**Rủi ro**:

| Rủi ro                              | Mức độ | Giảm thiểu                                  |
| ----------------------------------- | :----: | ------------------------------------------- |
| Accuracy drop > 10% → penalty       |  Cao   | Test trước GPQA; dùng group_size=64 nếu cần |
| vLLM V1 engine không tương thích    |  Cao   | Fallback: patch model.forward() trực tiếp   |
| Thời gian quantize > 120s startup   | Trung  | Quantize parallel, chỉ Linear layers        |
| torchao INT4 kernel chậm hơn Marlin | Trung  | Benchmark so sánh trước khi nộp             |

**Phương án triển khai (Build Image v15)**:

1. Base: `vllm-lfm25-fp8-kernels-v14` (đã có Triton kernel fused)
2. Thêm `torchao` package vào image
3. Sửa `python3_hijack`: sau khi vLLM load model FP8, apply `int4_weight_only()` lên `model.model.layers[*].mixer.*` (các Linear projections)
4. Rebuild CUDA Graphs sau khi quantize
5. Warmup 5 rounds → Ready to serve

import torchao
from torchao.quantization import int4_weight_only

## 6. PHÂN TÍCH WORKLOAD — TỐI ƯU HOÁ CHO GRADING TRACE

Từ `challenge_specification.md` Section 7:

```
70 conversations × 6 turns = 420 requests
Shared system prefix: 1000 tokens (tất cả conversations)
Per-conversation prefix: 1000 tokens
New user tokens/turn: 150
Output tokens/turn: 300 (cố định)
Max context: 4700 tokens (Turn 6)
```

**Ý nghĩa cho tối ưu**:

- ✅ `MaxLen=8192` đã đúng (max context 4700 + 300 output = 5000 < 8192)
- ✅ Prefix caching đang hoạt động trên V1 engine (APC mặc định bật)
- ✅ Recurrent state của LFM2.5 là bottleneck chính cho TTFT (không cache được)
- ⚠️ TTFT bị giới hạn bởi recurrent state recomputation O(seq_len) — cải thiện hạn chế
